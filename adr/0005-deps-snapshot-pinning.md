# ADR 0005 — Dependency snapshot pinning via `_deps.snap`

**Status:** Accepted

## Context

Dependencies are declared once, centrally, in the root `import_map.json` (ADR
0001), and consumed by bare alias — `@std/xml`, never `jsr:@std/xml@^0.1.0`.
Nothing inside a package records which version it builds against.

Dependency tracking has been through three shapes:

1. `deps.test.ts` files (PR #67) snapshotting **fully resolved URLs**
   (`https://jsr.io/@std/cli/1.0.25/mod.ts`), including files reached
   transitively through external packages. Every upstream patch release churned
   the snapshots, and failures arrived as test failures mixed in with real ones.
2. PR #90 cut that back to **direct dependencies recorded as the import-map
   specifier** (`jsr:@std/cli@^1.0.25`). The stated intent was to make snapshots
   _less_ sensitive to upstream: with the range in place of a resolved version,
   a patch release no longer touched the file.
3. PR #96 replaced the test with `_tools/check_deps.ts` and the `lint:deps`
   task, and moved to one JSON file per package keyed by entrypoint.

The founding commit describes the purpose as surfacing "which packages are
affected when `import_map.json` is updated". That reads like a review
convenience. **It is not.** It is the mechanism by which a dependency bump
becomes releasable at all, and that has never been written down.

## Decision

Each package has a `_deps.snap` file generated by `_tools/check_deps.ts`, keyed
by entrypoint, listing the **direct** external and workspace-internal
dependencies of that entrypoint's module graph. The lint task `lint:deps` checks
the snapshot against current resolution. Snapshots are updated by running:

```bash
deno run -A _tools/check_deps.ts --update
```

**External specifiers are recorded with their version constraint** —
`jsr:@std/cache@^0.2.1/memoize`, not `jsr:@std/cache/memoize`. This is
load-bearing; see below. Workspace-internal dependencies resolve to `file://`
URLs and are recorded as the bare alias, so the format is not uniform, and that
asymmetry is accepted.

### Why the version must stay

Release Please is configured in manifest mode with one entry per
`packages/<scope>/<name>` path (ADR 0003). It assigns a commit to a package by
**which files the commit touched**, not by the commit's scope. The commit type
then sets the bump level.

Proof from this repo's own history: `@binstruct/arp` v0.2.0 was cut by commit
`351f162`, whose scope is `feat(@hertzg/mac)`. It released `arp` because it
touched files under `packages/binstruct-arp/`. The scope appears only as
changelog text.

A dependency bump edits exactly one file: root `import_map.json`. That path
belongs to no package. If snapshots did not carry the version, a bump would
touch **nothing** inside any package directory, and Release Please would have no
way to attribute it — rewording the commit to `fix(@hertzg/xhb):` would not
help, because the type only sets the bump level for a commit some path has
already claimed.

The consequence would be silent: CI green, dependency updated in the repo,
package never republished, and JSR continuing to serve the old constraint to
consumers indefinitely.

Recording the version is what makes the bump touch
`packages/@hertzg/xhb/_deps.snap`, which is inside the package, which is what
makes it releasable.

## Consequences

- **Dependency bumps are attributable and therefore releasable.** The snapshot
  diff is the only thing tying a root-level version change to the packages that
  consume it.
- **Graph-shape regressions are caught** as well: a new dependency in a
  published package, a direct/transitive shift, an `npm:` specifier where a
  `jsr:` one was meant, a wrong subpath (`@std/encoding/base64` vs
  `/base64url`), a changed entrypoint set, an unintended edge between sibling
  workspaces.
- **Version bumps in `import_map.json` always require updating snapshots in the
  same commit.** This is not friction to be removed — removing it removes the
  release signal. Automate the regeneration if it is tedious; do not delete the
  data.
- Renovate authors its bumps as `chore(deps):`, which does not trigger a release
  under the default Release Please configuration. Shipping a dependency update
  to consumers means rewording the squashed commit to `fix(<scope>):` — which
  works **only because** the snapshot puts the commit inside the package path.
- Snapshot diffs are JSON-shaped and reviewable.
- New workspaces must include `_deps.snap` files alongside their entrypoints.
